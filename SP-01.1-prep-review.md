## F1 (H): E-SCHEMA scope vs the real Fastify adapter

The report states it "does not establish a future Fastify adapter's settings", which is honest. But the section still lists *rejected actor field*, *rejected email alias* and *rejected extra token field* as passed behaviours, and the "payload not mutated" assertion is presented as a strength.

Fastify's default Ajv options (*verify* in the installed `@fastify/ajv-compiler`):

| Option | Fastify default | Harness (inferred from "not mutated" + "rejected") | Effect |
| --- | --- | --- | --- |
| `removeAdditional` | `true` | off | With `additionalProperties: false`, extra fields (`actor`, `email`) are **silently removed**, not rejected. Request passes with 200/401 instead of 400. |
| `coerceTypes` | `'array'` | off | `"username": ["alice"]` becomes `"alice"`. Type-confusion inputs pass. |
| `useDefaults` | `true` | off | Defaults injected into the body. |
| Mutation | in place | never | The "payload not mutated" assertion is true of the harness and false by default in Fastify. |

Consequences:

1. "Rejected actor field" and "rejected email alias" are contract requirements (AC-01 area). Under Fastify defaults they become *stripped-and-accepted*. The spike must set Ajv options explicitly and assert 400, or the contract's rejection semantics are not met.
2. OpenAPI 3.0 vs 3.1 schema dialect differences (`nullable`, `exclusiveMinimum`, `example`) can make the contract schemas non-portable into Fastify's JSON Schema mode. *Verify* which OpenAPI version `workspace.openapi.json` declares and whether `scripts/contract-schemas.mjs` transforms it.
3. `ajv-formats` version and enabled formats may differ. "Malformed expiry rejected" depends on the `date-time` format being registered **and** strict.

**Action:** E-HTTP must reproduce all eight assertions through `fastify.inject()` against the real route, with Ajv options pinned in code, and compare to the E-SCHEMA table row by row.

## F2 (H): Response "rejected extra token field"

Response schemas in Fastify are compiled by `fast-json-stringify`. It does **not** validate. It drops unknown properties when `additionalProperties` is false and may coerce types. So a handler that accidentally returns `token` in the `Session` body would be **silently stripped** rather than rejected.

Stripping is arguably safer in production, but:

- the report/contract says "rejected", which will fail a test written from that wording;
- stripping hides handler bugs (the leak is masked, never surfaced in tests);
- the opaque-token cookie design (ADR-0025) needs a stated invariant: *token only in `Set-Cookie`, never in any body*.

**Action:** either reword the requirement to "never serialised", or add a test-only `onSend` hook that validates the pre-serialisation payload with Ajv and fails on extra fields. Include a test where the handler deliberately returns `token`.

## F3 (H): "Pass" with zero verified behaviours

> **Checklist:** Pass for concrete proposals, scope and available structural evidence; Gap for the full runtime spike…

Problems:

- "Pass" is self-assessed. The header says *Sequential author; no independent review or acceptance*. A checklist signed by the author alone should read **Self-checked**, not **Pass**.
- "Concrete proposals" is contradicted by the body: production expiry values and capability/transport decisions are explicitly not decided, and both ADRs are Proposed.
- "Available structural evidence" is lint/schema checks, which the report itself says "cannot substitute for E-HTTP/E-DB/E-SESSION".
- The mixed Pass/Gap line makes a machine- or skim-reader see "Pass".

**Action:** use a three-state vocabulary per row (`Pass-executed`, `Self-checked`, `Not run`), keep it per criterion, never aggregate. Keep the existing, good line "Handler behaviours verified: 0" at the top of the document, not the bottom.

## F4 (M): Source identity of a dirty worktree

The report chose not to "invent a commit". That is right, but it is a false choice. A base commit exists even when the work is uncommitted.

Missing:

- `git rev-parse HEAD` (the base the dirty tree sits on);
- hash of `git diff HEAD` (tracked changes) and a sorted list of untracked paths with their hashes;
- hash of the probe `schema-probe.mjs` and of `schema-result.json`. The probe is the experiment, and it lives untracked in `.tmp/`;
- Node binary identity (`process.version` is recorded, `process.versions` and platform/arch are not), and the exact `ajv`/`ajv-formats` resolved versions from the lockfile (the lockfile hash covers it only indirectly);
- the report says unrelated root/web package changes, preview/theme changes and submodule state exist in the same tree. `package.json` hash `323257b5…` therefore may include unrelated edits. The result is not attributable to SP-01.1 work.

**Action:** add the manifest script in `SP-01.1-spike-brief.md` (§ Evidence manifest). Prefer running future experiments from a clean `git worktree` at a recorded commit, with the spike in its own directory.

## F6 (M): Editing evidence to satisfy the linter

The first docs lint/test failed because the REG-00 v0.69 correction section was treated as current after the v0.70 bump. The fix relabelled the heading to *Historical*. This is plausible, but:

- it edits a document that serves as evidence, to make a check pass; the report asserts the original evidence/version is preserved, with no way to check without a commit;
- the linter's "current vs historical" detection is heading-driven. If it is heading-driven, relabelling any stale section passes it. That is a weakness of the check, not evidence of correctness;
- generated metadata was re-synchronised for 66 outputs after the edit. A before/after diff summary (what changed in which generated files) is not shown.

**Action:** commit the fix as its own commit with a message stating "lint heuristic fix, no evidence changed", and note whether the linter should key on version fields instead of headings.

## F7 (M): Synthetic parameters becoming policy

> Production policy decisions need not be invented to test labelled synthetic parameters.

Reasonable, but risky without a rule:

- KDF cost measured with a synthetic work factor on a dev machine gets quoted later as "login takes X ms";
- synthetic idle/absolute expiry (e.g. 60 s / 300 s so races are testable) will be copied into config.

**Action:** every synthetic parameter lives in one `SYNTHETIC` config block, prefixed in env (`SPIKE_SYNTH_*`), printed in the result file, and the result file states "non-binding; not a production value". KDF candidates that need native addons must be tested for installation on Node 24 (prebuilt binaries, build tools), since "compatibility" is the spike's purpose.

## F8 (L): Thin fixtures, no negative control

Eight assertions leave open: max length, whitespace/Unicode normalisation of usernames, case sensitivity, password length bounds, `null`/array/object in place of strings, extra nested properties, duplicate JSON keys, oversized body. There is also no **negative control**: no test proves the probe can fail (e.g. flip `removeAdditional` and watch one of the rejection assertions change). Without it, a probe that always passes is indistinguishable from a good one.

## F9 (L): Status vocabulary

Header: "Preparation In progress; E-SCHEMA passed, full compatibility/session spike Not run". Version: "0.1 Draft". Checklist: "Pass"/"Gap". Handoff: "Not started". Use one enum across the document set (`Not run | Run-failed | Run-passed | Self-checked | Accepted`) and state who may set `Accepted`.
