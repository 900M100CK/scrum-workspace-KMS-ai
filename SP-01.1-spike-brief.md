## 5. Session clock candidate and controlled races

Before E-SESSION execution, choose and record one **laboratory clock strategy**, without selecting production policy. Initial candidate: the session repository samples DB wall time after acquiring the relevant row lock, then validates and renews under the same short owned transaction. Login timestamps use the same authority. The app clock is for UI/measurements only. `now()`/CURRENT_TIMESTAMP are transaction-start time; substituting them for a fresh post-wait sample changes the experiment. See [PostgreSQL time functions](https://www.postgresql.org/docs/17/functions-datetime.html).

Use this algorithmic candidate, not unverified copy/paste SQL:

1. Begin the owning transaction; acquire the session row lock with a bounded wait. Unknown token returns no session.
2. After lock acquisition and any test barrier pause, sample the authoritative decision time once. Reject revoked session or decision time at/after either expiry. No renewal of expired state.
3. Compute `min(absolute_expiry, max(existing_idle_expiry, decision_time + idle_window))`. Renewal must not move expiry backwards or extend the absolute cap. Update only the locked row; check exactly one affected row and capture mandatory audit only if applicable.
4. Commit before acknowledging success. Logout uses the same row serialization discipline, preserves the original revocation time and returns idempotent declared 204 for an already-invalid token. Check operation outcomes and committed state.

A lock-protected read/check/write is permitted; an unprotected read-then-write is not. Passing an app timestamp captured before queueing is not equivalent. Preserve the old app-time algorithm only as an explicitly failing negative control for expiry regression/stale-time revival, never the intended implementation.

The DB wall clock can move backwards. This candidate does not prove otherwise: test and record its behaviour. Do not report skew/backstep protection unless implemented and observed. If it revives expired access after a backward step, record Run-failed for that guarantee and present an alternative (for example persistently detecting backward observations and failing closed); owner selection remains open. Merely asserting an invariant or clamping a timestamp without persistent evidence does not prove restart safety.

Deterministic tests use a **test-only repository clock seam sampled after lock acquisition**, carried through the actual transaction path. Separate them from runs sampling real clock_timestamp(); do not claim injected-time runs demonstrate the host/DB clock's real behaviour. Record precision/timezone and avoid reducing PostgreSQL microsecond boundaries silently to JavaScript milliseconds. No tests change the machine clock.

Synthetic expiry/KDF/load values live in one labelled immutable config; result.json records their sanitised values and `nonBinding: true`. Never print token/password/private-key material, even when synthetic. Production config must not import the spike config. Token entropy is an algorithm/source property; observed uniqueness is only a smoke check.

Required E-SESSION-07 schedules, each with bounded waits and cleanup:

- **Logout first:** logout acquires row lock, renewal is confirmed waiting, logout commits, renewal resumes and samples time; renewal fails due to revoked state, no successful renewal receipt.
- **Renewal first:** renewal acquires lock/validates, logout is confirmed waiting, renewal commits, logout commits; renewal may have succeeded, but subsequent access is 401. A delayed renewal HTTP response does not establish the database commit order.

Instrument lock acquisition/decision/commit acknowledgements through test-only events and verify waiting via the actual DB boundary, rather than sleeps or launch order. Preserve barriers, receipts and sanitised final-state observations. Add failure injection around these boundaries without using a hook as a replacement for the real repository implementation.
