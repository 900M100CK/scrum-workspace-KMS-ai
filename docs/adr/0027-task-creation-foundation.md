## Context and bounded disposition

Workspace already owns sessions, explicit capabilities, task/location storage, audit and idempotency. The current app registers session/project handlers only. Task routes exist in OpenAPI but have no implementation. P01 identified a private-provisioning gap, project-only outcome CHECKs, UUID-only paging traversal and the UC-03 creation-timestamp mismatch. This design reuses owned foundations and the existing read contract, not another service, receipt database, runtime agent or provider.

The [decision batch](../implementation/features/sp-03-create-task/decision-batch.md) is the authority for what the owner actually selected. Owner selection of a direction does not prove this ADR or its mechanisms implemented/tested. Existing ADRs remain unchanged and Proposed where applicable; this is a bounded SP-03 application proposal, not blanket adoption of ADR-0018/0019/0026.

## 1. Explicit create authority and advisory discovery

The owner selected project-scoped backlog-author with private audited provision/revoke/recovery, no role/creator auto-grant and no new delegation UI. A valid grant has subject_id=actor, project_id=target, resource_kind=project, resource_id=project_id, action=backlog-author and valid=true, together with current active membership and enabled authenticated account. PO/Admin/creator/member role text grants nothing. Public clients cannot assert actor/capability fields.

Extend the existing WorkspaceProjectOperator.project action union and private CLI whitelist with backlog-author; reuse expected revision, reason/operator identity, current account/member checks, clock → account → project → membership/grant ordering and co-committed private AuthorityProvisioningAudit. Extend the 007 audit action CHECK through new migration 009, not by editing 007, and add a separate partial unique index for one valid backlog-author grant per project/subject. Keep existing manager/admin uniqueness unchanged. Runtime receives no new private-audit or provisioning privileges.

Existing removeMember invalidates every individual capability; rejoin restores none. No task-create-specific exception may revive a grant. Project getAllowedActions adds listTasks for current members and createTask only for a valid explicit grant; advisory results never authorize the later command. Task-specific allowed-actions support is not needed for create/list/detail UI because SP-03 has no task mutations beyond creation. No role editor, public grant endpoint or initial creator author grant is added.

## 2. One client, lock order and failure decisions

All task business work uses one ownedTransaction runtime client, with existing bounded pool/lock/statement timeouts. Do not call sessions.inspect in a second transaction or copy session/permission policy into a new service.

1. Validate strict transport/body/selectors without accepting client identity. In the owned transaction call sessions.inspectInTransaction(c, token, false). Its current order is auth_clock_state FOR UPDATE → actor account via lock_auth_account → session row FOR UPDATE → trusted observation/validity. A typed denial returns a sentinel rather than throwing away a newly latched clock fault.
2. Resolve only project identity, then use current projectAccess(c, actor, projectId, false) to lock Project FOR UPDATE and require active membership. Do not pass manage=true, which checks membership-manage rather than backlog-author. Task detail first reads only a project-ID hint after authentication, then locks the project and re-reads the Task; no task lock precedes the project lock.
3. With the project guard held, inspect current explicit backlog-author for creation/replay. Reads require current membership only. Inspect actor/operation/key outcome after current authority; request hash covers createTask + canonical lowercase project ID + type + exact valid title + description defaulted to empty string. Reject all extra body/query/header shapes according to the declared contract; do not silently trim a stored valid title.
4. After relevant waits and before the first business write or protected result, call inspectInTransaction again on the same client. A failed guard returns no task effects/body; preserve typed current-auth/clock decisions as in the existing project transaction. All cooperating permission/account/task writers must use the shared guard protocol; this defines DB decision ordering, not socket/source handoff exclusion.
5. For creation, acquire the project lock before computing the append or touching task rows. No existing task row needs a lock for one insert. Future bulk task writers lock task IDs in ascending order after project; SP-03 does not implement them. Private grant changes lock their target account before project under the same clock guard. Do not introduce project → previously unlocked account acquisition into a new writer.
6. Co-commit Task, minimum business audit, trigger-maintained Backlog generation and immutable outcome. Use a server correlation ID and the UC-03 action backlog-item-create. On a known pre-COMMIT failure roll back every effect; uncertain COMMIT discards the client and returns controlled 503/unknown, never rollback certainty or a fresh automatic key. Do not perform network/LLM/UI work while holding the transaction.

Same-project same-key calls serialize through the project guard and existing outcome identity. Actor/operation/key uniqueness is retained across projects; changing project changes the payload hash and conflicts rather than creating a second entity under the same key. A unique/constraint conflict maps to controlled 409 without storage detail. Correctness must not rely on timing or merely launching Promise.all.

## 3. Append, Task origin and additive 009 safety

Under the project lock calculate the next position in PostgreSQL as coalesce(max(backlog_position),0)+1 over current Backlog rows. Never convert numeric positions or Backlog bigint generation through a JS number. Empty Backlog starts at position 1; negative or fractional existing positions preserve numeric ordering. Validate finite decimal wire representability; refuse unreconciled invalid legacy data, never silently coerce it.

Insert server UUID, selected type/title/description, state=todo, assignee_id=NULL, revision=1, location_kind=backlog, location_sprint_id=NULL and computed position. blocked=false follows empty committed blocker history. Migration 003's task_backlog_revision trigger already advances generation on Backlog insertion; no manual duplicate generation update. Backlog generation is a separate exact positive decimal string from Task/Project safe numeric revision. A transaction can generally advance generation more than once through storage transitions; clients compare equality rather than assuming a universal +1 rule. One SP-03 append produces the one existing insertion-trigger advance.

Recommended timestamp disposition, pending owner choice: add immutable server-created Task.created_at and required Task JSON created_at (RFC3339 UTC string) so UC-03 persists and returns the requested timestamp. Do not add a public created_by field or infer creator permissions; audit retains actor identity. Persist a DB-clock timestamp at millisecond precision once, expose its canonical UTC representation and reuse that same recorded creation time in the creation audit. Session clock precision/logic is unchanged. Existing task identity immutability comes from 003; an additive trigger protects created_at from updates.

If the owner instead retains the current Task API, this timestamp branch is not executable: revise the UC/source disposition and proposed migration/consumer plan explicitly before P03A. Do not silently drop UC-03 step 3/5 or pretend audit-only time was already the wire contract.

Migration 009-task-creation.up.sql is new. Before any DDL, refuse existing Task rows requiring creation-time reconciliation, any legacy createTask idempotency row or pre-existing backlog-author grant lacking the new supported provenance; retain all rows. No fabricated timestamps, implicit grant adoption or silent data backfill. This is intentionally bounded to a disposable clean task foundation; a valuable DB with legacy tasks needs separately reviewed reconciliation, not destructive reset.

With the recommended branch, 009 adds created_at/immutability, extends the private audit action constraint and separate valid-author uniqueness, and extends the existing outcome shape/immutability to createTask. Existing 001–008 bytes and every other operation's shape remain unchanged. Its down path refuses any Task, createTask identity, backlog-author grant/history or provisioning audit row that would lose required meaning. On an empty compatible fixture it restores original 008 CHECK/trigger definitions and removes only 009-owned artifacts. Up/repeat/empty reverse/forward, legacy/nonempty refusal and atomic failed-up/down all need disposable evidence. Refusal never authorizes deletion.

## 4. Exact original create outcome and data retention

Recommended retention disposition, pending owner choice: retain consumed actor/operation/key/hash and a minimal original typed 201 Task snapshot indefinitely, matching the existing permanent-receipt pattern. Snapshot content includes original title/description and, if selected, created_at; the owner must explicitly choose this retention consequence. No credential, cookie, private reasoning, HTTP header or generic full-response envelope is stored. Request payload is not duplicated separately; the key is never automatically recycled.

Extend workspace.idempotency_record, not a second result store. For createTask require committed state, expires_at=infinity, 64-character SHA-256 payload hash, nonempty key, result_status=201, result_ref equal to snapshot.task_id, and a strictly typed original Task body bound to its project. Preserve exact snapshot fields/JSON types, safe Task revision 1, initial todo/null-assignee/unblocked/Backlog location and exact position. Unknown/malformed/extra/null JSON must fail closed via IS TRUE validation or an equivalent total safe validator. Extend the existing immutable-outcome protection to createTask without weakening any existing project or protected-handoff operation.

Do not reuse the project Outcome.projectId=result_ref interpretation for tasks. A small tasks/outcomes.ts adapter returns project identity from the validated snapshot and task identity from result_ref; it uses the same owned client and hash identity. On replay, recheck current account/session, active project membership and backlog-author, hash binding and post-wait guard before returning the original 201 snapshot. UI separately refreshes current Task/list state. Later edits/removal/rejoin do not mutate the consumed outcome; rejoin restores no grant. No retention/deletion cleanup or key-ring feature is implicitly added.

Alternative not selected without an owner decision: return current mutable Task or expire/purge original content. Either changes original-result reconciliation/retention semantics and needs a concrete contract, tombstone/key-consumption and failure policy before P03. Pending retention answers block the dependent outcome implementation, not this design drafting.

## 5. Current Task projections and cursor traversal

Task detail/list require current authentication and membership, never a create grant or audit-read. All protected reads return the same generic 404 for missing/nonmember/foreign targets. Construct Task projections from current task location plus the highest committed blocker sequence; do not infer work_location from state or old allocations. A Done Backlog item remains in Backlog; Sprint/completed fixtures retain their actual discriminated location even though SP-03 adds no Sprint mutations.

Hold the project guard while reading ordered rows, membership revision/generation and project.backlog_revision in the same owned transaction, then recheck session validity before output. The selected protocol relies on cooperating task/blocker/permission writers taking that guard; document this as the DB boundary and test controlled writers. No cross-service/global snapshot or D-07 transport proof is implied.

Use the existing single SACW_PROJECT_CURSOR_KEY format and ProjectCursor HMAC codec unchanged, default TTL 300 seconds, internal fixed page size 50. No new public limit parameter, cursor table or key ring. Separate TaskStore page traversal from the ID-only ProjectStore.page helper:

- location=all: SQL order task_id ascending. location=backlog: SQL order backlog_position numerically, then task_id. Keep positions as exact strings, never lexical or floating-point comparisons.
- Scope fingerprint includes a task-list-v1 domain, actor, project, location filter, ordering name and page size. Projection fingerprint covers current membership revision/generation, exact Backlog generation and the complete canonical ordered Task projection, including every response field/derived blocked value and selected created_at. A valid same-actor relogin alone does not invalidate it.
- Store the last returned task UUID as the authenticated bookmark. After decode validates scope/MAC/generation/expiry, locate that UUID in the same fully sorted current projection and slice after its index. Do not filter IDs with greater-than when the order is numeric position. A verified bookmark absent from an otherwise matching projection returns generic 409, not partial data.
- Missing/misconfigured key or authority/storage failure is 503, malformed/foreign cursor is generic 400, verified stale/expired cursor is 409 with no items; revoked project remains the generic 404. No-store applies. Client discards accumulated pages on 409 and restarts. Single-key rotation invalidates old tokens according to the existing codec; there is no new availability claim.

Complete-projection hashing/read cost is an explicit existing-pattern trade-off, not a benchmarked scalability claim. Conservative invalidation preserves correctness. A later bounded benchmark may motivate a persisted generation optimization only if every projected change invalidates correctly. No premature cursor abstraction or duplicate pure codec test suite is required; PG/HTTP task-read tests verify the numeric/UUID bookmark traversal.

## 6. Proposed wire and input reconciliation

No contract changes occur in P02. Proposed P03A support, conditional on owner timestamp disposition: Workspace version 0.2.12 adds required Task.created_at as string/date-time (server-written, read-only); logical Task gains created_at; UC-03 is preserved, not silently weakened. Coordinate all Task producers/consumers and contract fixtures since strict old clients may reject an added field. Do not advertise backward compatibility for strict additionalProperties=false validators without consumer evidence.

CreateTask continues to accept only type/title/optional description. Reject whitespace-only title without changing the stored/hash form of a valid title; undefined description becomes empty string. Use the existing mutation transport pattern: exact Origin and X-SACW-Request:1, application/json with supported UTF-8 handling, no coercion/default removal, 8192-byte JSON body bound, controlled 400 malformed input, 413 oversized and 415 unsupported media. Add 413/415 to the existing createTask contract before enabling the handler. Return exact generic error shapes/no raw storage details. Task get rejects unsupported query selectors with a declared 400 added before implementation; invalid/missing identity itself remains generic 404 after authoritative checks. listTasks retains only cursor/location inputs and already declares 400/409.

The new task HTTP scope uses strict final output validation/serialization and no-store; actor/time/key values are not logged. Wire Task fields are never accepted as authority. Creation is independent of cursor-key availability; only list paging requires the key. Task UI advisory reads use project getAllowedActions; the actual mutation/reads always recheck current state.

## 7. Implementation split, verification and consequences

P03 is an aggregation parent, split into P03A contract/data/spec support, P03B additive persistence/outcome safety and P03C private audited author provisioning. Exact paths, existing/planned commands and producer assertions are in the feature decision batch/task cards. P04/P05/P06 follow selected persistence/authority/contracts; P07 starts with producers and closes before their verification; P08 browser and P09 integration remain separate. Default 006 session and 008 project fixture ceilings stay unchanged; task fixtures explicitly use 009. scripts/database.mjs already supports numeric through ceilings; no runner/root-script change is needed now.

Required future evidence: allowed/denied/role-identical author creation, revoked/rejoined authority, same-key/changed-body/lost-ack reconciliation, actual audit/outcome rollback, legacy/nonempty migration refusal, immutable timestamp/outcome and safe revision/position failures, controlled concurrent append/removal/expiry ordering, numeric pages with descending UUIDs/equal positions, stale/foreign/expired cursors, exact Task schema/media/body errors, fresh UI reload/recovery and separate trusted browser observations. Context/contracts/docs checks establish shape only; no DB/handler/browser test runs in P02.

Consequences: minimal Workspace service/storage reuse, explicit permission ownership, immutable evidence and provider independence; conservative full reads/clock-project guards may limit throughput and need target calibration later. Original result content is retained only if the owner chooses that policy. Timestamp schema changes require coordinated consumers, not just SQL. Legacy data is preserved by refusal. No direct source-send/socket exclusion, whole SC-01/SC-06, formal deployment, independent security or standards acceptance is claimed.
