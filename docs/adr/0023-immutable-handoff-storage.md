# Immutable handoff preparation and claim storage

**Artifact ID:** ADR-0023  
**Version/date:** 0.2 Proposed · 18 October 2026  
**Status:** Proposed additive PostgreSQL mapping under accepted ADR-0012; isolated verification supplied, application and relay acceptance open.  
**Inputs:** ADR-0004/0011/0012; Proposed ADR-0020 v0.2; SP-11; DATA-04; HANDOFF-REF-01; current owned SQL foundations.  
**Trace:** BR-08–BR-10, BR-12, BR-14; FR-21/28/29/32/55/57/59; SC-02/03/05/06; TC-26.

## Mapping and ownership

Knowledge migration 003 adds one immutable handoff_manifest row containing the complete discriminated evidence array, typed JSON and exact manifest bytes, plus append-only handoff_outcome rows. Keeping the evidence in the same row prevents an acknowledged manifest from being assembled from partially committed child rows. Stored byte SHA-256 is generated by PostgreSQL; the receipt reference is immutable. The manifest binds the existing execution's run/actor/project through a composite foreign key. Shape/identity/digest checks do not prove source authority or that the captured evidence was complete.

Workspace migration 004 reserves operation=protected_handoff in the existing owned idempotency_record, as ADR-0012 requires. Such rows are permanent consumed identities from insertion onward, retain pending as the generic record-state label, have infinity expiry and immutable claim_fence/process_ref, and cannot be updated into replay eligibility. A claim helper returns a fresh fence only for a newly inserted row; existing claims return no fence even after abort or process change. Append-only protected_handoff_outcome rows retain Workspace's own observations against the exact claim fence. Knowledge and Workspace never write each other's database.

The fresh claim must commit and its acknowledgement must be known before the handler acquires the guard. A generated receipt/fence inside an uncommitted transaction is not durable acknowledgement. Client timeout or transaction rollback does not authorize sending. Existing/unknown claims, unresolved transport and old process tokens never authorize resume. Active process fencing, current authority, transport quarantine and guarded byte checks remain application responsibilities; storing a process reference is not proof that they exist.

## Failure, migration and alternatives

The SQL preserves exact bytes and rejects incomplete/extra-key evidence shapes, duplicate source IDs, actor/project/run mismatch, invalid encoded JSON or raw JSON differing from the typed record. It stores only identities/digests/context references, never provider payloads, excerpts or private reasoning. Final source/policy/lifecycle/observation validation still occurs through current authoritative adapters.

Runtime roles receive only required insert/read rights on new append-only tables; ordinary idempotency continues separately. Protected rows/outcomes are not automatically pruned. Upgrade aborts if legacy protected_handoff rows exist, rather than guessing their send/fence status or deleting them. Down migrations refuse nonempty protected records; valuable data needs reviewed forward recovery, never a reset to regain a handoff ID.

Using ordinary expiring idempotency without a reserved operation permits replay after cleanup. A separate claim store would diverge from the accepted idempotency mapping. Normalized mutable evidence children complicate atomic complete preparation. The selected additive mapping retains service ownership and the accepted boundary, with explicit storage and index overhead. Physical retention outside nonreplayable claims remains an owner decision.

## Verification and handoff

Verify on a disposable synthetic database: forward/repeat/empty reverse, failed upgrade rollback, byte/digest/typed identity and full-evidence shape constraints, immutable runtime access, owning-transaction rollback, claim duplicates including changed digest/process, matching outcomes and legacy reserved-row rejection. Exercise concurrent duplicate claims and verify only one fresh committed fence. Do not apply to the development database as part of those tests.

This is a storage slice, not a provider/gateway/permission implementation. API, SP-09/11 Done and live TC-26 remain open until real handlers/adapters prove current scope, persistence failure/unknown acknowledgement, claim/fence/crash/guard and actual zero-byte rejection/completed handoff. Checklist: Pass for bounded mapping and failure design; Gap for application and relay evidence. Owner approval is not implied by author implementation or tests.

## Executed isolated evidence

PostgreSQL 17.10 / pgvector 0.8.2 passed the new 11-result handoff suite and existing 15-result storage suite, including parent tests. Exact bytes/typed identity, immutability/rollback, duplicate and concurrent claims, permanent identity, outcome-fence binding, nonempty down refusal and legacy upgrade rollback were exercised under runtime/owner contrasts. Both uniquely named containers were stopped; the development database was not migrated by this work. The queue records final data/diagram checks. A generated receipt/fence is still not a durable acknowledgement until transaction commit is known.

## Prepared-record projection follow-up

[HANDOFF-SQL-01](../sdlc/references/handoff-sql-projection-2026-10-18.md) supplies a seven-parameter trusted-context SQL read and StoredHandoff projection. Canonical base64 strips only PostgreSQL line separators from the encoding of exact stored bytes; it never reserializes manifest JSON to recover bytes. Optional integration passed seven results for both purposes, selector mismatches/NULL, encoding/precision negatives, consumed-claim separation and uncommitted/rolled-back visibility. These selectors are not permission decisions and no authenticated HTTP lookup/guard/provider handler is implemented.
