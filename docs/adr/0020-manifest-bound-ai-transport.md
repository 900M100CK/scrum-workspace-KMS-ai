# Manifest-bound internal AI transport

**Artifact ID:** ADR-0020
**Version/date:** 0.3 Proposed · 18 October 2026
**Status:** Proposed interface design implementing owner-confirmed ADR-0012; storage/adapters/guard and runtime acceptance remain pending.
**Inputs:** PRD-01 v0.9; SAD-03 v0.14; DATA-04 v0.10; ADR-0011/0012/0013; Workspace v0.2.8 / Knowledge v0.2.9; SYS-01. The initial v0.1 snapshot used SAD v0.12, DATA v0.7 and Workspace v0.2.7 / Knowledge v0.2.6.
**Trace:** BR-08, BR-09, BR-10, BR-12, BR-14; FR-14/21/25/26/28/29/32/55/57/59; SC-02, SC-03, SC-05, SC-06; TC-26.

## Decision and ownership

Workspace's provider-input request and Knowledge's buffered answer response carry a complete immutable StoredHandoff record plus the exact frozen payload bytes. Both contracts share identical HandoffManifest, discriminated HandoffEvidence and StoredHandoff schemas. Purpose-specific wrappers prevent answer records from authorising provider input or vice versa. ProviderPayload remains typed question/configuration/document-context/operational observations. InternalQuestionResult replaces bare operational IDs and a single aggregate source revision with the complete mixed manifest evidence. These are internal envelopes, never browser or provider permission assertions.

Knowledge alone persists preparation and append-only outcomes. Its authenticated internal getHandoffManifest returns an exact complete committed record by handoff_id, scoped to the current actor/session/project/run. Workspace resolves this record outside its guard and compares the complete supplied receipt and frozen binding. A receipt, digest, complete=true, caller identity field or source ID alone grants no authority. Remote lookup/persistence failure or unknown commit sends no protected bytes. The internal record is never in the public-action catalogue or forwarded by the browser gateway.

## Exact bytes and full evidence

StoredHandoff contains manifest, manifest_bytes_base64, manifest_digest and durable_commit_ref. Knowledge freezes UTF-8 JSON manifest bytes and commits the record and complete evidence atomically; SHA-256 hashes those exact bytes. The manifest digest and receipt are outside those manifest bytes, avoiding a self-referential hash. Decode with strict base64/UTF-8/JSON validation; reject duplicate JSON keys, trailing data and parsed values unequal to the typed manifest. Hashes are lowercase 64-hex SHA-256. Do not normalize whitespace, Unicode, array order or reserialize before hashing. This protocol needs no unselected JSON canonicalization scheme.

ProviderInput.payload_bytes_base64 contains the final provider-specific request JSON; its immutable allowlisted adapter must validate the complete semantic mapping to typed ProviderPayload, including instructions/question/configuration and all authorized context, rejecting any extra hidden evidence. Provider wire JSON need not equal the internal semantic object. The answer envelope decodes directly to its typed QuestionResult. Compare the exact decoded byte length and SHA-256 against manifest.payload_length/payload_digest. Only those validated frozen bytes can be handed off. Provider serializers/adapters must freeze the final provider request, including instructions/model configuration and authorized context, before preparation; ProviderPayload.provider_configuration_id identifies the immutable adapter configuration. If an adapter adds instructions or rewrites JSON after freezing, it must prepare a new payload/manifest. An actual provider-specific wire schema remains an adapter prerequisite; no provider is selected here. Browser output is only frozen QuestionResult bytes, never the internal envelope, manifest or receipt.

destination_ref resolves to a server-owned immutable transport/configuration reference, not a client-selected URL. Provider purpose binds the selected allowlisted provider configuration and its exact final bytes; answer purpose binds the authenticated response channel. actor_id/access_context_ref/session_generation/project_permission_revision are checked against current authoritative session/project state. run_id/attempt_id/handoff_id and destination must agree across the owning run, prepared record, payload and transport. Claim support, factual correctness and permission are checked separately from digest equality.

Each document evidence entry binds project/source/document/version/passage, current permission and lifecycle revisions, version digest and excerpt digest. Each operational entry binds project/source/entity kind/entity ID/entity revision, observation revision, observed_at and exact entity-snapshot digest. Decimal revision strings preserve owned bigint precision; conversion from existing numeric transports must be exact, never rounded. Workspace observations still come from current operational records; historical embedded text is no replacement.

The manifest contains the full evidence used to prepare the context/draft, including uncited passages/observations, not just visible citation chips. Reject duplicate or conflicting source-ID mappings. Provider passages must match exact document entries and excerpt bytes; every observed entity must match its own operational entry and snapshot/revision/time. Document version digests bind immutable source bytes; lifecycle/policy changes are rechecked independently. For an answer, every citation must map to the matching evidence kind/locator; the manifest retains uncited generation inputs as well. Zero-evidence insufficiency is possible but cannot disguise omitted used context. Empty candidate evidence does not justify a fabricated provider-backed answer.

## Durable one-use claim and guarded delivery

1. Knowledge freezes payload and manifest, commits them outside any Workspace guard and acknowledges durability. Unknown acknowledgement is reconciled under the same preparation identity/digest; no send while unknown.
2. Workspace verifies the committed receipt through getHandoffManifest outside the guard. Its request key equals handoff_id. Workspace durably inserts actor/protected_handoff/handoff_id bound to manifest_digest in its owned claim/idempotency storage. Only a fresh confirmed claimant can proceed. Duplicate, changed, failed or unknown claims authorize no transmission. Protected claims cannot expire, be pruned into replay eligibility or be reused after abort/restart.
3. Acquire the applicable project/session guard. Compare the complete immutable receipt and exact frozen bytes, current session/project AND document scope, source availability/lifecycle and every operational identity/revision/observation. Existing final evidence validation is authenticated and scoped; it does not recursively acquire the guard. No remote preparation/claim write or retry wait occurs under the guard. A changed source requires fresh preparation after releasing it.
4. Only a matching permitted attempt can hand off frozen bytes while the guard remains held through known completion or confirmed abort. A mismatch sends zero bytes. Revoked/invalid original answer evidence withholds the whole original draft; bounded replacement requires a new generation/support validation and fresh immutable attempt, never trimming the old envelope.
5. Persist/report outcomes separately. Unknown transport is not rollback and cannot cause automatic replay or a new-ID resend. Claim fencing on process restart must prevent an old claimant from resuming; unresolved transport quarantines affected handoffs until reconciliation. A committed preparation or claim does not prove delivery. Exactly-once external receipt is not promised.

## Historical storage design before additive SQL

Logical model v0.5 adds complete receipt/byte-binding fields and the Workspace ProtectedHandoffClaim mapping. Knowledge additive immutable manifest/evidence/outcome storage and Workspace nonexpiring one-use claim/fence enforcement are still required. Existing general idempotency expiry is insufficient for protected claims. Applied migrations remain unchanged and no new SQL migration is supplied in this design correction. Do not start provider relay implementation based only on these schemas.

TC-26 must exercise both purposes: persistence failure/unknown ack, altered manifest or payload bytes/digest/length, purpose/run/actor/project/destination mismatch, omitted uncited evidence, multiple operational entities with distinct revisions/times, revocation/lifecycle/state change before and inside final checks, duplicate/unknown claim, crash/restart/fence and unknown transport. Assert zero protected bytes on rejection and guard retention through a valid completion/abort. Include a document-plus-operational answer whose uncited task changes; it cannot pass using the cited document's revision alone. Contract negatives check selected declarations only; no storage, actual transport or concurrency evidence is claimed.

**Checklist:** Pass for interface ownership, exact binding, failures and requirement trace; Gap for additive storage, provider-specific final-wire schema, consumer/provider tests and live TC-26. **Handoff:** SYS-01 transport design supplied; AI relay remains blocked on those runtime prerequisites. No accepted ADR, business scope, provider or application framework is changed.

## Executable reference follow-up — 18 October 2026

[HANDOFF-REF-01](../sdlc/references/handoff-byte-reference-2026-10-18.md) supplies synthetic byte-binding tests, not a store/relay implementation. The reference transport profile checks canonical base64, fatal UTF-8/JSON with no BOM/duplicate decoded keys/unpaired surrogates, exact safe-integer manifest/answer numbers, raw byte digests/lengths, complete evidence and answer locators. It does not normalize source bytes. Limits come from trusted caller configuration; fixture sizes select no application bound. Provider-specific fractional-number/wire mapping remains an adapter prerequisite. Numeric values that cannot be represented exactly must fail rather than round; public wire-format changes remain separate contract work. No storage/claim/guard/current-access/transport gate is closed by this checker, and the decision remains Proposed.
