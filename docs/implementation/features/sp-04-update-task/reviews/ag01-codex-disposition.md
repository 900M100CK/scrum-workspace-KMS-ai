## Findings reconciled

1. **Typed outcomes — implementation prerequisite, not a proven current production incident.** Migration 009's project_outcome_shape admits typed result_status/result_snapshot only for createProject/addMember/removeMember/createTask. It excludes the proposed new Task 200 and Blocker 201 receipts. Existing Task outcome code also hardcodes createTask. Static inspection supports the need for additive storage design; no SQL failure was executed in this reconciliation. The report's Critical severity is treated as a blocker for enabling future producers, not a current SP-03 defect. P02 also needs to cover protect_project_outcome: the current immutability trigger protects the existing operation names only. Extending shape validation alone would not establish retained SP-04 result immutability. Applied 009 remains unchanged; the next migration number is determined from the current inventory when implementation begins.
2. **Action provisioning — confirmed readiness gap.** Add no implicit PO/Admin/member rights. Exact grant names/scope, private operator/audit extensions and replay-authority semantics belong to P02. Current capability storage can hold more action strings; safely issuing and auditing them is the missing path. Whether disabled target accounts are assignable is not settled merely by the report saying NOT disabled: current AC-43 names current membership. Reconcile that additional target-eligibility rule explicitly with current account/membership policy before treating it as a Must.
3. **Locking — retain as a design/verification obligation, not a reproduced deadlock.** projects/store.ts transaction first calls sessions.inspectInTransaction, which locks the singleton clock, actor account and session. removeMember then locks the target account **before** projectAccess locks Project; it subsequently locks target membership and assigned Tasks in task_id order. Thus the report's proposed Project → target Account/Membership → Task order is not a faithful statement of the existing complete order. The common singleton clock currently serializes cooperating transactions; different later row order alone does not prove a current deadlock under that protocol. P02 must reconcile the complete actual order, all cooperating runtime/operator writers and post-wait expiry; P03/P06 must later test the real setAssignee/removeMember producers in both orders. No new lock strategy is selected here.
4. **413/415 — coordinated future contract support.** Confirmed for the new mutation operations only, as C04 explains. Do not claim all existing Task endpoints have an undeclared-status defect or hide an intentional public status behind a framework label. Define the body/media boundary and coordinate the operation contract before enabling it.
5. **Audit/state/scope history — preserve existing Must evidence without chart expansion.** business_audit has timestamps and before_ref/after_ref text; the createTask audit currently records revision:1, while its original retained create result already contains initial state/content. Absence of those fields from the create audit alone does not prove an SP-03 defect or absence of the initial state elsewhere. Future state audit must satisfy UC-04's before/after-state requirement using explicit values or resolvable retained identities; revision references without historical state would not demonstrate this. Assignee-null/removal encoding already exists in removeMember. sprint_allocation alone lacks transition times; actual SP-05 audit producers must later establish scope history. The report's string encodings are proposals, not the sole valid representation. No chart, scheduler, event table, estimate field or broad historical-data migration is authorised.
