## 1. Recommendation: C4 primary views, 4+1 coverage

**Proposed documentation choice:** Use C4 Context and Container diagrams as the principal architecture entry. Add focused sequence, state and ER diagrams for behavior/data. Retain the SAD's 4+1 sections as a coverage crosswalk and a useful academic narrative. Do not maintain two independently authored copies of the same architecture. This recommendation changes documentation organization, not the owner's two-service decision, scope, stack or accepted ADRs.

C4 organizes structural views by zoom level; its author recommends using only levels that add value and says Context/Container suffice for many teams. Components are optional; a container is an application or data store, not necessarily a Docker container. See the primary [C4 diagram guide](https://c4model.com/diagrams), [component guidance](https://c4model.com/diagrams/component) and [container definition](https://c4model.com/abstractions/container).

Kruchten's [original 4+1 paper](https://arxiv.org/abs/2006.04975) separates logical, process, development and physical concerns, tied together by scenarios. It is not obsolete because it predates C4. The two approaches answer different questions and are not a one-to-one mapping.

For one engineer, five months and two services, the recommendation is to minimize duplicate maintenance while preserving concurrency/security detail. If the assessment rubric requires 4+1, present the existing SAD sections with this crosswalk and reuse the same figures:

| Concern | Primary evidence / proposed figure | Limit |
| --- | --- | --- |
| System scope and external actors | New C4 Context | Identity/provider choices remain explicitly conditional; no invented integration |
| Logical responsibilities | C4 Container plus focused ERD/domain model | Existing DGM-ARCH-01 is a composition sketch, not automatically a complete C4 diagram |
| Process/concurrency | Existing AI/read flows plus handoff and creation sequences | A sequence must specify races, retries and failure, not just the happy path |
| Development organization | SAD §4 and repository package map; C4 Component only when useful | Package ownership and runtime components are different concerns |
| Physical environment | Deployment view for the actual target environment | Proposed ports/processes are not measured or deployed facts |
| +1 scenarios | UC-01–UC-13 and SC-01–SC-08 → views → tests | A drawn path is not evidence that a scenario passed |

N/A for now: manually maintained C4 Code diagrams and a complete second 4+1 picture set. They would duplicate evolving implementation detail. This report does not claim the planned C4/sequence/state/ERD figures already exist.
