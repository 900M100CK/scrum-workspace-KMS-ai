## 2. Recommended technical baseline

### 2.1 Complete transaction protocol and lock hierarchy

Every task mutation executes within a single PostgreSQL transaction managed by `WorkspaceProjectStore.transaction` (`services/workspace/src/projects/store.ts`). All cooperating writers must strictly follow this acquisition sequence:

```mermaid
flowchart TD
    Step1["1. Singleton clock: auth_clock_state (FOR UPDATE via clockLock)"] --> Step2["2. Actor auth_account: lock_auth_account(actor_id)"]
    Step2 --> Step3["3. Actor session: SELECT ... FROM session FOR UPDATE"]
    Step3 --> Step4["4. Target auth_account (if setAssignee): lock_auth_account(target_user_id)"]
    Step4 --> Step5["5. Project row: SELECT ... FROM project FOR UPDATE (projectAccess)"]
    Step5 --> Step6["6. Target membership (if setAssignee): SELECT ... FROM membership FOR UPDATE"]
    Step6 --> Step7["7. Target task row: SELECT ... FROM task WHERE task_id = $1 FOR UPDATE"]
    Step7 --> Step8["8. Transaction Guard: recheck session expiration after lock waits"]
    Step8 --> Step9["9. Idempotency outcome check / Business writes / Audit / Save outcome"]
```

**Key Concurrency Invariants:**
1. **Clock serialization:** Because step 1 acquires the PostgreSQL row lock on `auth_clock_state`, all cooperating transactions in `services/workspace/` are serialized at the transaction boundary. No database deadlocks occur between `setAssignee` and `removeMember`.
2. **Post-wait guard:** Step 8 calls `await guard()`, re-evaluating whether the actor's session expired during any lock wait. If expired, the transaction rolls back cleanly with HTTP 401/503 before any business write or audit record is emitted.
3. **Optimistic revision validation:** Once the `task` row is locked (step 7), the handler verifies `task.revision.toString() === expected_revision`. If mismatched, it immediately throws `conflict()` (`409 state_conflict`).

### 2.2 Additive Migration 010 specification (`010-task-mutation-outcomes.up.sql`)

Migration 010 introduces typed outcome shape validation and immutability triggers for the 4 new SP-04 operations, alongside auditing support for the 4 new action capabilities:

```sql
-- 1. Extend authority_provisioning_audit CHECK constraint for mutation actions
ALTER TABLE workspace.authority_provisioning_audit
  DROP CONSTRAINT authority_provisioning_audit_action_check,
  ADD CONSTRAINT authority_provisioning_audit_action_check CHECK (
    action IN (
      'create-project',
      'membership-manage',
      'project-administrator',
      'backlog-author',
      'task-edit',
      'task-state',
      'task-assign',
      'task-blocker'
    )
  );

-- 2. Define outcome validation functions for Task and Blocker snapshots
CREATE OR REPLACE FUNCTION workspace.valid_task_outcome_snapshot(value jsonb, reference text) RETURNS boolean
LANGUAGE plpgsql IMMUTABLE AS $$
BEGIN
  IF jsonb_typeof(value) <> 'object' THEN RETURN false; END IF;
  RETURN (value->>'task_id') = reference
    AND (value->>'project_id') IS NOT NULL
    AND (value->>'title') IS NOT NULL AND length(value->>'title') >= 1
    AND (value->>'state') IN ('todo', 'in_progress', 'done')
    AND (value->>'type') IN ('story', 'bug', 'task')
    AND (value->>'revision') ~ '^[1-9][0-9]*$'
    AND (value->>'created_at') IS NOT NULL;
END $$;

CREATE OR REPLACE FUNCTION workspace.valid_blocker_outcome_snapshot(value jsonb, reference text) RETURNS boolean
LANGUAGE plpgsql IMMUTABLE AS $$
BEGIN
  IF jsonb_typeof(value) <> 'object' THEN RETURN false; END IF;
  RETURN (value->>'event_id') = reference
    AND (value->>'task_id') IS NOT NULL
    AND (value->>'status') IN ('open', 'resolved')
    AND (value->>'sequence') ~ '^[1-9][0-9]*$'
    AND (value->>'recorded_at') IS NOT NULL;
END $$;

-- 3. Extend project_outcome_shape CHECK constraint on idempotency_record
ALTER TABLE workspace.idempotency_record
  DROP CONSTRAINT project_outcome_shape,
  ADD CONSTRAINT project_outcome_shape CHECK (
    (
      operation = 'createProject'
      AND result_status IN (201, 204)
      AND (
        (result_status = 201 AND workspace.valid_project_creation_snapshot(result_snapshot, result_ref))
        OR (result_status = 204 AND result_snapshot IS NULL)
      )
    ) OR (
      operation = 'addMember'
      AND result_status = 204
      AND result_snapshot IS NULL
    ) OR (
      operation = 'removeMember'
      AND result_status = 204
      AND result_snapshot IS NULL
    ) OR (
      operation = 'createTask'
      AND result_status = 201
      AND workspace.valid_task_creation_snapshot(result_snapshot, result_ref)
    ) OR (
      operation IN ('editTask', 'setTaskState', 'setAssignee')
      AND result_status = 200
      AND workspace.valid_task_outcome_snapshot(result_snapshot, result_ref)
    ) OR (
      operation = 'recordBlocker'
      AND result_status = 201
      AND workspace.valid_blocker_outcome_snapshot(result_snapshot, result_ref)
    ) OR (
      operation NOT IN (
        'createProject', 'addMember', 'removeMember', 'createTask',
        'editTask', 'setTaskState', 'setAssignee', 'recordBlocker'
      )
      AND result_status IS NULL
      AND result_snapshot IS NULL
    )
  );

-- 4. Update protect_project_outcome trigger function to protect all 8 operations
CREATE OR REPLACE FUNCTION workspace.protect_project_outcome() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  IF OLD.operation IN (
    'createProject', 'addMember', 'removeMember', 'createTask',
    'editTask', 'setTaskState', 'setAssignee', 'recordBlocker'
  ) THEN
    RAISE EXCEPTION 'Committed project outcomes are immutable' USING ERRCODE = '23514';
  END IF;
  RETURN OLD;
END $$;
```

**Rollback Specification (`010-task-mutation-outcomes.down.sql`):**
- Verifies that no retained idempotency records or authority audit records exist with the 4 new mutation operations/actions before rolling back.
- Restores migration 009's exact functions and constraints.

### 2.3 Completed-Sprint reopening mechanics (`setTaskState`)

When reopening a task from a completed Sprint (`location_kind = 'completed'`) to active state (`state = 'todo'`):
1. In accordance with migration 003 constraint `task_location_shape` (`003#L40-44`):
   - A task cannot have `location_kind = 'completed'` unless `state = 'done'`.
   - Therefore, changing `state` from `done` to `todo` requires atomically updating `location_kind = 'backlog'` and `location_sprint_id = NULL`.
2. Existing trigger `preserve_completed_allocation` (`003#L110-120`) prevents modifying rows in `sprint_allocation` whose `allocation_state = 'completed'`. The handler must **not** update or delete the completed allocation row; it leaves the completed historical allocation intact.
3. Existing trigger `advance_backlog_revision` (`003#L89-108`) will automatically increment `project.backlog_revision` when the task's location transitions back to the Backlog.

### 2.4 Highest-sequence blocker projection & sequence allocation

1. **Atomic sequence allocation:** In `recordBlocker`, the next sequence number for `task_id` is computed under the task row lock:
   ```sql
   SELECT COALESCE(MAX(sequence), 0) + 1 AS next_seq
   FROM workspace.blocker_event
   WHERE task_id = $1
   ```
   This guarantees that sequence numbers are strictly contiguous and monotonically increasing without collision against `UNIQUE(task_id, sequence)`.
2. **Current blocked status:** Existing projection logic in `services/workspace/src/tasks/store.ts#L41,55`:
   ```sql
   COALESCE((
     SELECT status = 'open'
     FROM workspace.blocker_event
     WHERE task_id = t.task_id
     ORDER BY sequence DESC
     LIMIT 1
   ), false) AS blocked
   ```
   correctly derives `blocked = true` if and only if the event with the highest sequence is `status = 'open'`.
